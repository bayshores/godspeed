## 6.2 Interviews and mocks

Getting ready for an interview, online assessment or test is a normal space the learner's own agent sets up from its screen; there is no separate kind of space.

- **Interview deadlines.** A deadline may have kind `interview` (no "due", like an exam) and an `aboutFileId`: a space info file on what it is like, usually `What it's like.md` (space format 11, `core::spaces::space_deadlines`; reader drops id once file is gone). `GET /api/spaces/{id}/deadlines/{deadlineId}/about` gives its text, or 404 when file is empty or not text.
- **Setting one up.** Tool texts tell teacher to add posting as space info, interview with date and time, `What it's like.md` as `about_file_id` (searched for first, under 200 words, only sources it read) and a `Study guide.md` it writes as a study file in `file_ids`, so deadline's topics fill once extraction has run. `add_space_file` writes such a file from `name` and `text`; one it wrote before by that name (upgrade's two files count) is replaced and keeps its id.
- **The upgrade from preps.** A space saved as a prep by 0.6.5 or before (a `prep` on its record) is upgraded once at server start, before it serves (`core::spaces::prep_upgrade`, run by `services::spaces::upgrade_old_preps`). What it was like becomes `What it's like.md`, its topics `Study guide.md`, its day an interview deadline, its goal description when that is empty, and its mocks belong to deadline. A prep with no day, or a day that can't make a deadline, gets record's `waitingDeadline` instead; adding a deadline with that `id` takes its place (window's Add date sends it; agent's next interview from `add_space_deadline` takes it, after `read_space` showed it as an interview with no date). Ids come from space id, so an upgrade stopped halfway writes same things again next time, and reader keeps `prep` as saved until last write drops it.

A mock is one run of questions like the real thing on an exam, quiz or interview deadline (`core::mocks::mock`), saved as `spaces/<id>/mocks/<mockId>.json` (format 2; format 1 reads as 2), with `services::mocks::mocks` its only writer.

- Mocks are numbered per deadline; a deadline has max one unfinished mock, and takes one only when not done and it has a topic with facts or an about file the about route can read (the page shows Take a mock only under the same test). A mock is 1 to 10 questions with no time limit or 5 to 240 minutes. Removing a deadline removes its mocks.
- Agent writes all questions before it starts and grades all answers after it ends (`agent::subagents::mock_writer`); clock runs with no agent. The writer gets deadline, what it is like and its topics weakest first with up to 5 facts each, and tags each question with the `fact_ids` it tests; with no facts it writes from what it is like alone (`fromAbout`). The grader gets each question with its facts and, for a timed mock, how often and how long it was paused.
- Each request waits on bridge until an agent takes it. A request does not outlive server, so at startup, after upgrade from preps, every mock still waiting for questions or grades asks again, and one whose time ran out while server was off ends then and asks (`ask_waiting_mocks`, `services::mocks::mocks`). A mock with its request out shows as being written or graded; one whose request failed shows why, with Try again (and Remove this mock while it has no questions).
- A timed mock can be paused: it keeps seconds left, refuses answers and runs, and on resume runs for that long. Each pause is recorded. A running timed mock whose time ran out is ended at its end time next time it is read (`services::mocks::mock_end`); a paused one never is.
- A graded question with `factIds` counts as an answer for those facts (`mock_answers`, passed to `derive_progress` by `progress_for`).
- "Run examples" runs learner's JavaScript or Python with computer's own Node or Python, max 5 seconds and 1 MB of output (`core::mocks::mock_run`, `services::mocks::mock_runner`).
